Documentation

A JSON analytics engine, documented the way it's queried

Dot-path and filter queries over large JSON files. Built across three modules — a JSON parser, a query parser, and a query executor — each documented here with real pseudocode, verified behavior, and diagrams matching the actual codebase.

01 — system architecture

How the pieces fit together

The JSON Parser reads the input file once and produces an in-memory tree. The Query Parser independently turns a query string into a small structure describing what's being asked. The Query Executor takes that parsed query and walks the tree to produce a result. This separation means parsing the JSON and parsing the query are decoupled — each can be optimized independently, and many queries can run against one parsed file without re-parsing it each time.

Dashed boxes are either in-progress (AaronSimd) or intermediate data, not a running process (Parsed JSON tree, Parsed query). The dashed arrow from the JSON file into AaronSimd marks that path as not yet wired into the default build.

JSON Parser

Converts raw JSON text into an internal tree representation. Parsed once, reused across every query against that file.

Query Parser

Parses dot-path queries (with wildcard and array-index support) and GET/FROM/WHERE filter queries — including AND, OR, and NOT — into a small structure the executor can walk.

Query Executor

Walks the parsed tree using the parsed query, resolving keys, array indices, and wildcards, and evaluating filter conditions row by row.

Indexer

Builds lookup structures so repeated queries against the same file don't require re-scanning it from scratch each time.

02 — json parser

Two implementations, two platforms

There are currently two JSON parser implementations in this project, built for different goals. AaronJsonParser is the primary, cross-platform parser — a straightforward single-pass character loop that runs identically on macOS and Windows, and is what every query in this system actually runs against today. AaronSimd is a separate, in-progress SIMD-accelerated parser using AVX2 instructions — significantly faster, but x86-only, so it currently runs on Windows and not on Apple Silicon.

AaronJsonParser primary macOS + Windows

Builds the tree in two passes: indexStructure() walks the raw buffer once, character by character, producing a flat list of tokens (structural characters, string spans, value spans). constructTree() then walks that token list once more, using a stack of node pointers to build the actual nested tree.

loadFile(filename)

open file in binary mode
IF file failed to open:
    print error, RETURN false

seek to end, record file size
seek back to beginning

adjustedSize = round size up to the next multiple of 32
resize buffer to adjustedSize, padded with spaces

read the file into the buffer

IF read failed:
    print error, RETURN false

RETURN true

indexStructure()

Single linear pass over the buffer. Tracks two pieces of state as it goes: whether it's currently inside a string, and whether it's currently in the middle of reading a bare value (a number, boolean, or null).

FOR each character c at position i in the buffer:

    IF currently inside a string:
        result = detectString(c)
        IF result is not "none":
            close the current string token at position i, mark it type "string"
        CONTINUE to next character

    IF currently reading a bare value:
        IF c is whitespace or a structural character:
            close the current value token at position i-1

    IF c is a quote:      push new token, enter/exit string mode via detectString(c)
    ELSE IF c is [ ] { } , or : push the matching structural token
    ELSE IF c is whitespace:  skip
    ELSE IF not currently reading a value:
        push a new token, classify its type via detectType(c)
        mark that a bare value is now being read

constructTree()

Consumes the token list from indexStructure() in order, using a stack of pointers into the tree being built.

nodes = empty stack of node pointers
currentKey = ""

FOR each token in the token list:

    IF token is an object-start or array-start:
        create the matching container node
        IF stack is empty:      this becomes the root
        ELSE IF top of stack is an object:  attach it under currentKey
        ELSE IF top of stack is an array:   append it
        push the new node onto the stack

    ELSE IF token is a string:
        IF the NEXT token is a colon:
            this string is a KEY -- save its text as currentKey
        ELSE:
            this string is a VALUE -- create a leaf node storing its
            source start/end position, attach/append it the same way

    ELSE IF token is a number, boolean, or null:
        create the matching leaf node, attach/append it the same way

    ELSE IF token is an object-end or array-end:
        pop the current container off the stack

Leaf values store positions, not copies

Every leaf node (string, number, boolean) stores only its start and end byte position in the original buffer — never a copy of the text. Reading a value's actual text (for display, or for a WHERE comparison) means slicing that range out of the buffer at the moment it's needed. This is why the buffer itself has to stay alive for as long as the tree does.

AaronSimd in progress x86 / Windows only

A separate, SIMD-accelerated parser using AVX2 instructions to scan 32 bytes of the input at a time, rather than one character at a time. Built for raw throughput on large files; not yet integrated as the default parser, and doesn't run on Apple Silicon since AVX2 is an x86-only instruction set.

indexStructure() — SIMD variant

prepare SIMD lookup tables for JSON structural characters

FOR each 32-byte block of the buffer:

    load 32 bytes into a SIMD register
    split each byte into a low nibble and a high nibble
    use lookup tables on both nibbles to identify structural characters
    combine the lookup results into a structural-character mask

    compare all 32 bytes in parallel against the quote character
    compare all 32 bytes in parallel against the backslash character

    find escaped quotes (odd-length backslash runs) and remove them
    from the quote mask

    find which byte positions fall inside a string, using the
    corrected quote mask, and remove any structural characters that
    fall inside a string from the structural mask

    WHILE the structural mask still has bits set:
        find the next set bit's position and the character there
        record the matching token (object/array start or end, colon,
        comma) at that position
        clear that bit from the mask

Reference: the structural-scanning technique here follows the approach described by Geoff Langdale and Daniel Lemire in Parsing Gigabytes of JSON per Second.

03 — query parser

Turning a query string into structure

Two query forms are supported: plain dot-path queries, and GET/FROM/WHERE filter queries. Both are parsed by QueryParser::parse(), which checks for a leading GET and routes to the matching parser. Both parsers share one function for reading a path expression — parsePath() — since a path is needed in every clause of both query forms.

parsePath(input, i)

Converts a raw path expression into a list of steps — a plain key, an array index, a wildcard, or a bracket-quoted key. A bracket-quoted key exists specifically to address object keys that dot-notation itself can't express: a literal "." key would collide with the path separator, and an empty-string key has no bare-identifier form at all.

path = empty list of steps

WHILE i has not reached the end of input:

    IF current character is whitespace: STOP

    IF current character isn't '[' and can't start a bare key:
        THROW "expected key"

    IF current character is not '[':
        read a bare identifier (letters, digits, underscore)
        add it as a Key step

    IF current character is '[':
        move past '['
        IF end of input: THROW "unclosed bracket"

        IF next is '*':          add an AllElements (wildcard) step
        ELSE IF next is a digit or '-':
            read the index digits
            IF negative: THROW "negative indices not supported"
            add an ArrayIndex step
        ELSE IF next is '"':
            read characters until the closing '"'
            add a Key step using that exact text
        ELSE: THROW "invalid bracket contents"

    IF whitespace reached: STOP

    IF more input remains:
        REQUIRE the next character to be '.'
        move past it
        IF input ends right after the dot: THROW "trailing dot"

RETURN path

A bracket segment always needs a . before it, with one exception: an array index or wildcard directly attached to a bare key (items[0]) doesn't need one, kept for backward compatibility. A quoted key does need the dot (items[0].["key"]) — see the Query Language Reference for the full rule.

parseFilterQuery(input)

Parses the GET ... FROM ... WHERE ... form. WHERE is optional; when present, it reads one or more conditions, each of which may be negated with NOT and chained to the next with AND or OR.

REQUIRE "GET" keyword
selectField = parsePath(...)
IF empty: THROW "expected field after GET"

REQUIRE "FROM" keyword
sourcePath = parsePath(...)
IF empty: THROW "missing source path"

IF "WHERE" keyword present:
    REPEAT:
        condition = new Condition

        IF "NOT" keyword present:
            condition.negative = true
            move past NOT

        condition.field = parsePath(...)
        IF empty: THROW "expected field after WHERE"

        read the comparison operator (=, !=, <, <=, >, >=)

        IF value starts with ' or ":
            remember which quote character opened it
            read until the matching closing quote
            IF no closing quote found: THROW "unterminated value"
        ELSE:
            read the value until the next whitespace

        condition.value = the value read
        add condition to the filter query

        IF "AND" keyword follows:
            move past it, CONTINUE to next condition
        ELSE IF "OR" keyword follows:
            mark THIS condition's word-operator as Or
            move past it, CONTINUE to next condition
        ELSE:
            STOP reading conditions

IF unread characters remain: THROW "unexpected trailing input"

RETURN the filter query

The word-operator is stored on the condition that PRECEDES the connector — conditions[i].wordOperator is the operator joining condition i to condition i+1. The executor uses this to group conditions so that AND binds tighter than OR — see the Query Executor section for how that grouping and short-circuiting actually works.

Supported today

= != < <= > >= comparison operators · AND / OR chaining · NOT negation · single- and double-quoted values · bracket-quoted keys for special object keys

04 — query executor

Walking the tree with a parsed query

Two traversal algorithms cover every query: executeStep for dot-path queries (returns a list, since a wildcard can produce many results), and resolveSingle for anywhere only one result is possible or needed, like a WHERE condition's field lookup — it skips the heap allocation a list would need.

executeStep(node, path, stepIndex, results)

IF node is null:
    append null to results   -- prints as "DNE"
    RETURN

IF stepIndex has reached the end of path:
    append node to results   -- full path consumed, this is the answer
    RETURN

step = path[stepIndex]

SWITCH step.type:
    Key:
        IF node is an object AND it has this key:
            executeStep(that child, path, stepIndex+1, results)
        ELSE:
            append null to results

    AllElements (wildcard):
        IF node is an array:
            FOR EACH element in the array:
                executeStep(element, path, stepIndex+1, results)
        ELSE:
            append null to results

    ArrayIndex:
        IF node is an array AND the index is in range:
            executeStep(that element, path, stepIndex+1, results)
        ELSE:
            append null to results

resolveSingle(node, path, stepIndex) → node or null

Same shape as executeStep, but returns one pointer instead of appending to a list — and a wildcard step can't be represented as a single result, so it always resolves to null.

evaluateCondition(row, condition) → true/false NOT support

fieldNode = resolveSingle(row, condition.field)

IF fieldNode is null:
    RETURN false   -- missing field never matches, negated or not

result = compareValues(fieldNode, condition.operator, condition.value)
RETURN condition.negative ? NOT result : result

Design decision: a missing field is its own category, not a comparison outcome — the same principle behind the DNE/null distinction elsewhere in this system. NOT never turns "the field isn't there" into a match.

evaluateWhere(row, conditions) → true/false AND/OR support

The word-operator connecting two conditions is stored on the first one — conditions[i].wordOperator joins condition i to condition i+1. AND binds tighter than OR (same convention as most languages), so the condition list is treated as OR-separated groups of AND-connected conditions: a AND b OR c AND d groups as (a AND b) OR (c AND d).

IF conditions is empty: RETURN true   -- no WHERE clause, everything matches

anyGroupMatched = false
currentGroupFailed = false

FOR i from 0 to conditions.size - 1:

    IF NOT currentGroupFailed:
        IF NOT evaluateCondition(row, conditions[i]):
            currentGroupFailed = true   -- short-circuit rest of this AND-group

    isLast = (i is the last condition)
    groupEndsHere = isLast OR conditions[i].wordOperator is Or

    IF groupEndsHere:
        IF NOT currentGroupFailed:
            anyGroupMatched = true
            BREAK   -- short-circuit: whole WHERE is true, stop checking further groups
        currentGroupFailed = false   -- reset for the next OR-group

RETURN anyGroupMatched

Short-circuits at both levels: stops evaluating an AND-group the moment one condition fails, and stops checking further OR-groups the moment one group fully matches. A conditions list with no OR at all collapses to exactly one group — identical performance to a plain AND-only chain.

executeFilterQuery(root, filter) — GET / FROM / WHERE

sources = executeStep(root, filter.sourcePath)

FOR EACH source in sources:
    IF source is null OR not an array:
        CONTINUE          -- FROM must resolve to an array

    FOR EACH row in the array:
        IF NOT evaluateWhere(row, filter.conditions):
            CONTINUE      -- row excluded

        selected = executeStep(row, filter.selectField)
        append all of selected to results

RETURN results

Usage

parser p;
p.loadFile("data.json");
p.indexStructure();
p.constructTree();

QueryParser qp;
Query q = qp.parse("GET name FROM store.products WHERE category = electronics AND inStock = true OR category = furniture");

auto results = executeQuery(p.getRoot(), q, p.getJsonData());
for (const auto* node : results) {
    std::cout << nodeToString(node, p.getJsonData()) << std::endl;
}
05 — query language reference

How to actually write a query

There are two query forms: dot-path (retrieve a value at a location) and filter (GET/FROM/WHERE — scan an array, select matching rows).

Dot-path segments

SegmentSyntaxExampleMeaning
Bare keyidentifiernameLook up an object key by plain name
Array index[N][0]The Nth element of an array (0-indexed)
Wildcard[*][*]Every element of an array
Quoted key["text"]["product name"]Look up a key with a space, empty string, or lone dot

The one rule most likely to trip you up

Every segment needs a . before it — including bracket segments — except an array index or wildcard attached directly to a bare key (items[0], kept for backward compatibility). A quoted key still needs the dot: items[0].["product name"] is valid, items[0]["product name"] throws Expected '.'.

Filter queries

GET <path> FROM <path> [WHERE <condition> [AND|OR <condition> ...]]
  • FROM must resolve to a JSON array — anything else returns an empty result, not an error.
  • WHERE is optional — omitted entirely means every row is returned.
  • Conditions may be prefixed with NOT, and chained with AND or OR. AND binds tighter than OR: a AND b OR c means (a AND b) OR c, not left-to-right.
  • Values with spaces need quotes — either 'single' or "double" both work.

What happens when things go wrong

SituationBehavior
Malformed syntax (typo, unclosed bracket, trailing dot)Throws an exception with a message
A key doesn't existReturns "DNE" — not an error
Array index out of rangeReturns "DNE"
Wildcard on a non-arrayReturns "DNE"
Wildcard on an empty arrayReturns zero results — not an error, not DNE
A real JSON null valueReturns the string "null" — deliberately distinct from DNE
FROM resolves to a non-arrayReturns zero results — does not throw
Negative array index ([-1])Throws at parse time
Unquoted WHERE value with a spaceThrows — quote it instead
NOT on a field that doesn't existNever matches — missing stays its own category, not flipped into a match

Complete examples

# Quoted key on a wildcarded array
store.products[*].["product name"]

# Filter query, no WHERE at all
GET name FROM store.products

# AND / OR together — binds as (a AND b) OR c
GET name FROM store.products WHERE category = electronics AND inStock = true OR category = furniture

# NOT
GET name FROM store.products WHERE NOT inStock = true

# Double-quoted value
GET price FROM store.products WHERE name = "Wireless Mouse"
06 — diagrams & testing

Build structure and verified behavior

CMake structure

Top-level CMakeLists.txt builds json_engine (the library — parser.cpp + QueryParser.cpp) and test_executor (the CLI, links against json_engine), then includes tests/ via add_subdirectory.

tests/CMakeLists.txt builds engine_tests (currently just test_query_executor.cpp), linking json_engine and GTest::gtest_main — GoogleTest itself is pulled in via FetchContent, not vendored. gtest_discover_tests sets its working directory to the repo root, so relative paths to test_data_*.json resolve the same way whether run through ctest or the built binary directly.

Control flow

The program's control flow has four real decision points: did the file load, did the query parse, which query type is it (dot-path vs. filter), and are there more queries to process. The first two both funnel failures into a caught, printed error rather than a crash — malformed input never takes the program down. The third is the one true fork in execution; the fourth is what turns the program into a loop rather than a one-shot run.
